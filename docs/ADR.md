# SYSTEM ARCHITECTURE SPECIFICATION: ЦЕХ РЫБОПЕРЕРАБОТКИ (OMNICHANNEL RETAIL & B2B PORTAL)

## 1. PRIMARY INTENT (Целеполагание системы)

* **Генеральная бизнес-цель:** Увеличение оборота цеха по переработке рыбы, реализующего продукцию через небольшой магазин и выездную торговлю, с последующим выходом в сегмент групповых и мелкооптовых заказов.
* **Оперативная цель (горизонт 3–6 месяцев):** Увеличение выручки действующих розничных каналов (магазин и выездная торговля) за счет расширения круга знающих о точке покупателей, перевода обезличенного трафика в собственную оцифрованную базу в 1С и удержания клиентов в активном состоянии через регулярную доставку актуального прайса.
* **Тактическая цель (горизонт 1–2 года):** Комплексное масштабирование сбыта, автоматизация клиентского сервиса и формирование собственного медиа-охвата по пяти направлениям:
  1. **Развитие B2B и групповых предзаказов:** формирование канала прямых предварительных заявок (совместные покупки, коллективные заказы, мелкий опт) для прогнозируемой загрузки производственных мощностей цеха.
  2. **Легковесная система лояльности:** внедрение простых и прозрачных механик поощрения постоянных покупателей (без перегрузки кассового и учетного контура) для роста частоты повторных покупок и среднего чека.
  3. **Омниканальная интерактивная связь:** расширение присутствия за счет подключения интерактивных ботов в Telegram и ВКонтакте в единую связку с сайтом и ботом MAX.
  4. **Интеграция ИИ-агента:** подключение интеллектуального ассистента к клиентским каналам и базе знаний цеха для автоматизации консультаций (по продукции, наличию, условиям заказа) и помощи в формировании заявок.
  5. **Медиа-экспансия и ИИ-фабрика контента:** запуск и автоматизированное ведение информационных и видеоканалов (MAX, Telegram, ВК, VK Видео, YouTube) с генерацией прогревающего контента (обзоры продукции, процессы цеха, рецепты) для органического привлечения новой аудитории.
* **Ключевая метрика успеха на старте:** Динамика вовлеченности по воронке касаний (посещаемость сайта, количество прямых скачиваний прайса, запросов разовой отправки на Email и активных обращений к боту MAX), конверсия посетителей в подписчиков базы 1С и рост частоты повторных покупок без нарушения требований 152-ФЗ и ФЗ-38 «О рекламе».

## 2. INTENT DOMAIN BRIEF (Доменная модель и границы контекстов)

### 2.1. Предметная область и правовой контур
* **Товарная матрица витрины:** Регулярный возобновляемый ассортимент (не оперативные остатки кассы), синхронизируемый из выделенного регистра 1С с монотонной версией и штампом даты актуальности.
* **Идентификация и учетные записи:**
  * Единый первичный ключ клиента — `Email` (логин пользователя).
  * Полноценная учетная запись: парольная аутентификация и механизм сброса пароля через подтверждение по Email.
  * Опциональные профильные атрибуты: `Телефон`, идентификаторы мессенджеров (`max_user_id`, `tg_id`, `vk_id`).
  * Отказ от сбора ФИО и иных персональных данных для минимизации регуляторной нагрузки по 152-ФЗ.
  * Соблюдение ст. 18 ФЗ-38 «О рекламе» обеспечивается 3-шаговым конвейером регистрации-подписки с обязательным подтверждением почты (Double Opt-In) и аудиторным журналированием факта согласия.

### 2.2. Границы подсистем (Bounded Contexts)
1. **Контур 1С (Master Data, Loyalty & Marketing Core):**
   * Ведение регистра регулярного ассортимента и выгрузка данных на сайт.
   * Хранение мастер-базы подписчиков и клиентов, управление статусами верификации («прямой контакт») и оптовыми условиями.
   * Генерация прайса по единому мастер-шаблону и выполнение регулярных рассылок по индивидуальным графикам.
   * Прием и обработка входящих пакетов подписчиков, отписок и заказов в машиночитаемом формате `JSON` через единый REST API или файловый шлюз.
2. **Контур «Толстый Django» (Public Edge, Document Engine & Integration Hub):**
   * **Инфраструктура, топология контейнеров и входной периметр (Nginx):** система разворачивается через Docker Compose на одном хосте и разделена на 5 изолированных долгоживущих сервисов (`nginx`, `web`, `worker`, `postgres`, `redis`) и одноразовый служебный контейнер миграций (`migrate-job`). Сервисы `web` (WSGI-сервер `gunicorn~=23.0`) и `worker` (`python manage.py run_worker`) запускаются из единого неизменяемого версионированного образа (многоступенчатая Docker-сборка на базе `ghcr.io/astral-sh/uv:latest`), разделяя общую кодовую базу, но имея независимый жизненный цикл и масштабирование. Единственной публичной точкой входа является reverse proxy **Nginx** (опубликованы только порты `80`/`443`), который изолирует внутреннюю сеть Docker, терминирует TLS, передает заголовки проксирования (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`), динамически отслеживает IP реплик `web` на уровне `upstream`-группы с фоновым ре-резолвингом через встроенный DNS Docker (`upstream web_upstream { zone web_upstream 64k; server web:8000 resolve; resolver 127.0.0.11 valid=10s ipv6=off; keepalive 32; }`, `proxy_pass http://web_upstream`) — без ручного перезапуска, с сохранением keepalive-пула и балансировкой по всем репликам; требует OSS nginx >= 1.27.3 и защищает `/admin/` вторым независимым рубежом (IP allowlist и/или HTTP Basic Auth) до передачи запроса в Django. Статика собирается на этапе билда образа (`collectstatic --noinput` с `CompressedManifestStaticFilesStorage` в prod и plain `StaticFilesStorage` в dev/тестах) и в production отдается напрямую через Nginx из разделяемого read-only тома `static_volume`, разгружая процесс Python.
   * **Стек слоя представления:** Django Templates (SSR) + HTMX + Alpine.js (для быстрой бесшовной реактивности в веб-браузере и внутри MAX Mini App).
   * **Стек REST API:** Django Ninja + Pydantic v2 (строгая валидация общих контрактов обмена из `services.exchange.contracts` и высокая скорость обработки запросов 1С).
   * **Слой хранения, изоляция состояния и очередь задач:** контейнеры с кодом (`web`, `worker`) строго stateless — все персистентное состояние вынесено во внешние тома, переживающие пересоздание, масштабирование и откат контейнеров приложения. СУБД PostgreSQL (`postgres:17-alpine`, внешний том `pgdata`, без публикации порта `5432` наружу, проверка готовности `pg_isready`, регулярный логический бэкап `pg_dump` вне контейнера) хранит основные бизнес-данные, `JSONField` анкет, пользовательские сессии (`SESSION_ENGINE` в БД при едином `SECRET_KEY` в окружении для сохранения сессий при обновлении реплик `web`) и персистентную таблицу очереди `BackgroundTask` с механизмом аренды `locked_until`, версией контракта `schema_version` и конкурентным захватом через `SELECT FOR UPDATE SKIP LOCKED`. Контур Redis (том `redisdata`, без публикации порта наружу, проверка `redis-cli ping`) обеспечивает скользящее окно Rate Limiting через `IRateLimiter` и оперативное кэширование. Внешние I/O-операции (SMTP, файловый шлюз) выполняются строго вне транзакций БД.
   * **Фоновый исполнитель (`worker×N`):** отдельный масштабируемый сервис (`cli/worker_runner.py`, запускаемый через Django management-команду `run_worker`) без использования Celery. Поддерживает горизонтальное масштабирование (`--scale worker=N`) без простоя `web`, фильтрацию захватываемых задач по поддерживаемым `task_type` и `schema_version`, штатное завершение текущей задачи по сигналу `SIGTERM` (`stop_grace_period`), координацию поллинга входящей директории файлового шлюза `/exchange/1c_to_web/` между репликами через блокировку БД (`pg_try_advisory_lock`) и публикацию `heartbeat` для контроля жизнеспособности.
   * **Публичная витрина:** информация о цехе, интерактивная навигация к магазину у «Пятерочки», график выездной торговли, экранный прайс со штампом актуальности.
   * **Генератор, импорт и кэш прайса:** разделение build-time шаблона `assets/templates_xlsx/price_master_template.xlsx` (`PRICE_TEMPLATE_PATH`), технических адаптеров `openpyxl` (`ICatalogXlsxParser` / `IOrderXlsxParser` в `integrations/xlsx/openpyxl_parser.py` и `IXlsxRenderer` в `integrations/xlsx/openpyxl_renderer.py`) и runtime-кэша `price.xlsx` (`PRICE_XLSX_FILENAME`, хранится в общем для `worker` и `web` именованном томе `/app/cache` через интерфейс `IStorage`). Ручная загрузка каталога из `.xlsx` выполняется через защищенный `/admin/` (`UploadedFile` в потоке `BinaryIO` без добавления bind-томов) напрямую в PostgreSQL; ручное помещение файлов в `/app/cache` запрещено. Файловый шлюз `/exchange/` также вынесен в общий том без публикации по HTTP и без монтирования в Nginx.
   * **Разовая выдача прайса:** условное отображение кнопки скачивания на главной странице по `storage.exists()`, возврат `FileResponse` или `Http404` в веб-слое при запросе `/price/download/`, а также разовая отправка на Email (защита через Honeypot в веб-формах, `IRateLimiter` и `ICaptchaProvider` со Stub-заглушкой для разработки).
   * **Клиентский контур:** разделенные сценарии управления аккаунтом (`account_service.py`: регистрация с паролем, подтверждение Email, сброс пароля) и подпиской (`subscription_service.py`: 3-шаговый мастер, согласие, отписка).
   * **Composition Root и конфигурация:** централизованный DI-контейнер `config/container.py` (`get_storage()`, `get_catalog_xlsx_parser()` с Этапа 2), строгая валидация неизменяемых (`frozen=True`) доменных настроек через `pydantic-settings` в `config/env.py` с сокрытием секретов через `SecretStr`, однократным разрешением каскада `.env` + `.env.{APP_ENV}` и защитой от Path Traversal, а также поэтапное подключение приложений в `config/settings.py`.
3. **Контур мессенджеров (Channel Adapters — старт с MAX в Релизе 1.2):**
   * Выдача актуального `.xlsx`-прайса в один клик без предварительной регистрации.
   * Запуск 3-шагового мастера подписки через встроенное мини-приложение (MAX Mini App) со склейкой `max_user_id` и `Email`.

### 2.3. Интеграционные протоколы и контракты (`1С <-> Django`)
Взаимодействие строится на базе **единых транспортно-независимых контрактов (`services/exchange/contracts.py`)** через два взаимозаменяемых транспортных канала:

1. **Единый эндпоинт REST JSON API (`/api/v1/exchange/`):**
   * Единая точка входа для синхронного структурированного обмена.
   * Прием и передача типизированных JSON-конвертов с маршрутизацией в `services/exchange/` по полю `event_type`:
     * `PRICE_SYNC` — выгрузка товарной матрицы регулярного ассортимента из 1С на сайт.
     * `SUB_SYNC` — передача подтвержденных профилей и анкет подписчиков из Django в 1С.
     * `UNSUB_EVENT` — передача событий отписки пользователей из Django в 1С.
     * `ORDER_CREATE` — передача B2B и групповых заказов (Релиз 2.0).
     * `ACK_RECEIPT` — подтверждение успешного приема и фиксации пакета в БД (квитирование).
   * Авторизация по Bearer-токену со сквозным контролем номеров сообщений (`msg_no` / `received_no`) и идемпотентной дедупликацией.
2. **Файлово-пакетный механизм обмена (Файловый шлюз `/exchange/`):**
   * **Назначение:** передача тяжелых бинарных данных (заполненные файлы заказов `.xlsx`, шаблоны, медиа), ручной контроль на этапе внедрения и резервный транспорт при сбоях сети или недоступности API.
   * **Структура директорий:**
     * `/exchange/1c_to_web/` — входящие пакеты для сайта от 1С.
     * `/exchange/web_to_1c/` — исходящие пакеты сайта для 1С.
     * `/exchange/archive/` — успешно обработанные пакеты.
     * `/exchange/error/` — сбойные пакеты для ручного разбора администратором/менеджером.
   * **Именование и нумерация:** префиксы узлов (`1C`, `WEB`) и сквозные монотонные номера (`{SENDER}_{RECIPIENT}_{MSG_NO}`).
   * **Состав пакета:**
     * Файл-манифест `*_meta.json`: `sender`, `recipient`, `msg_no`, `received_no`, `timestamp`, `event_type`, список вложенных файлов с их контрольными суммами `sha256`.
     * Файлы полезной нагрузки: `*_payload.json` (данные) и/или `.xlsx` (файловые заявки, мастер-шаблоны).

## 3. ARCHITECTURE DECISION RECORDS (Ключевые архитектурные решения)

### ADR-001: Архитектура «Толстый Django», изоляция адаптеров XLSX и защита от устаревших сборок
* **Контекст:** Требуется обеспечить круглосуточную выдачу прайса с минимальной нагрузкой на CPU веб-сервера, отделить правила чтения/формирования матрицы от работы с `openpyxl`, исключить «второй источник истины» при ручном наполнении каталога до запуска `PRICE_SYNC` и предотвратить перезапись `price.xlsx` устаревшей параллельной сборкой.
* **Решение:** Django хранит единственную реплику ассортимента в PostgreSQL. Composition Root вынесен в `config/container.py` (`get_storage()`, с Этапа 2 — `get_catalog_xlsx_parser()`). Работа с `openpyxl` полностью изолирована в `integrations/xlsx/` за протоколами `core/interfaces.py`: чтение `.xlsx` выполняется через `ICatalogXlsxParser` / `IOrderXlsxParser` (`integrations/xlsx/openpyxl_parser.py`, потоковый `BinaryIO`, `read_only=True, data_only=True`), генерация — через `IXlsxRenderer` (`integrations/xlsx/openpyxl_renderer.py`) по мастер-шаблону `PRICE_TEMPLATE_PATH`. Ручная загрузка каталога (основной способ наполнения на Этапах 2–3, с Этапа 4 — аварийный admin-fallback) идет через форму Django Admin (`/admin/` защищен вторым рубежом Nginx по ADR-009/010) из `UploadedFile` в `services/catalog_service.py` без добавления bind-томов в `docker-compose.yml`, выполняя транзакционный `upsert` слепка `Category`/`Product` (с деактивацией отсутствующих позиций) и инкремент `CatalogSyncMeta.version`. Том `/app/cache` остается монопольной зоной `services/xlsx_generator.py` (`IStorage` с защитой от Path Traversal, `fsync` и атомарной перезаписью); до запуска рендерера на Этапе 5 `storage.exists()` возвращает `False`, и кнопка `/price/download/` скрыта штатно. Обновление каталога, инкремент `CatalogSyncMeta.version` и постановка задачи на сборку прайса выполняются в одной транзакции БД, а публикация файла защищена проверкой актуальности версии (Stale Artifact Protection).
* **Последствия:** Чистая инверсия зависимостей (`services/` не зависит от `integrations/`); отсутствие расхождения между экранным прайсом, генерируемым `price.xlsx` и валидацией заказов в 2.0; отсутствие новых bind-томов и изменений в `docker-compose.yml`/`deploy.sh`/`cc.sh`; гарантия консистентности кэша `price.xlsx` при конкурентных обновлениях; простая изоляция ФС в тестах через `tmp_path` и двустороннюю очистку кэша `get_storage.cache_clear()` в фикстурах (до и после выполнения).

### ADR-002: Двойная интеграционная шина с общими контрактами и транзакционной идемпотентностью
* **Контекст:** Требуется исключить Email-транспорт, обеспечив обмен через REST API и файловый шлюз по единым схемам данных с защитой от дублирования пакетов при сетевых повторах.
* **Решение:** Транспортно-независимые схемы конвертов вынесены в `services/exchange/contracts.py` и переиспользуются в `api/` и `integrations/file_gateway/`. Обработка протокола выделена в `services/exchange/processor.py`, а маршрутизация в прикладные сервисы — в `services/exchange/handlers.py`. Дедупликация для обоих транспортов выполняется через `ExchangePacketLog` по ключу `(sender, msg_no)` и сверке `sha256`. Применение данных пакета, запись в журнал аудита и сдвиг `received_msg_no` в `ExchangeNodeState` фиксируются в единой транзакции БД, а квитанция `ACK_RECEIPT` выпускается строго после коммита.
* **Последствия:** Исключение повторного применения изменений при ретраях 1С; единая кодовая база контрактов для REST и файлов; точная семантика `ACK_RECEIPT`.

### ADR-003: Разделение управления аккаунтом и 3-шагового конвейера подписки (`JSONField`)
* **Контекст:** Регистрация аккаунта, восстановление пароля и маркетинговый онбординг подписки имеют разные состояния, правила валидации и причины изменения.
* **Решение:** Кастомная модель `User` (`AUTH_USER_MODEL = "users.User"`, `email` как логин, хэш пароля, флаг верификации, статус подписки, `JSONField` анкеты). Минимальный скелет `db/users/` (`User(AbstractBaseUser, PermissionsMixin, TimeStampedModel)`, регистронезависимый индекс `UniqueConstraint(Lower("email"))`, `UserManager`, `UserAdmin` без `username`, миграция `0001_initial.py`) вводится на Этапе 1 строго до первого запуска `migrate-job`, а бизнес-атрибуты добавляются аддитивными миграциями на Этапах 2–8. Прикладная логика разделена на два сервиса:
  1. `services/account_service.py`: регистрация с паролем, подтверждение Email, генерация и проверка одноразовых токенов сброса пароля.
  2. `services/subscription_service.py`: сохранение `JSONField`-анкеты (Шаг 2), фиксация согласия по 152-ФЗ и ФЗ-38 (Double Opt-In, Шаг 3), проверка допустимости переходов статуса подписки и запись исходящих событий `SUB_SYNC` / `UNSUB_EVENT` в той же транзакции БД. Управление HTTP-сессиями и cookies остается в слое `web/`.
* **Последствия:** Соблюдение SRP в прикладном слое; атомарная фиксация изменений подписки и событий для 1С без утечки деталей транспортного конверта в бизнес-сценарий; исключение конфликта `InconsistentMigrationHistory` с `django.contrib.admin` и сохранение стратегии Expand/Contract на персистентном томе `pgdata` (ADR-009) без его пересоздания перед Этапом 2.

### ADR-004: Персистентная очередь в PostgreSQL (`locked_until`), горизонтальное масштабирование `worker×N` и идемпотентность внешних вызовов
* **Контекст:** Требуется выполнять фоновые задачи без Celery с поддержкой горизонтального масштабирования (`--scale worker=N`) и независимого обновления воркеров, гарантировав восстановление задач после аварийного падения процесса (`SIGKILL`), отсутствие гонок на файловом шлюзе `/exchange/1c_to_web/`, совместимость контрактов в окне смешанных версий и защиту от дублей писем при ретраях.
* **Решение:** Таблица `BackgroundTask` в PostgreSQL включает поле времени аренды `locked_until` (lease timeout) и версию схемы полезной нагрузки `schema_version`. Инфраструктурный цикл опроса вынесен в `cli/worker_runner.py` (запускается из `cli/management/commands/run_worker.py`). Репозиторий `db/tasks/repositories.py` захватывает в короткой транзакции через `SELECT FOR UPDATE SKIP LOCKED` задачи в статусе `PENDING` или зависшие `PROCESSING` с истекшим `locked_until`, фильтруя выборку строго по поддерживаемым текущей версией кода `task_type` и `schema_version` (исключает захват задач нового формата старым воркером в окне rolling-обновления). Опрос входящей директории файлового шлюза `/exchange/1c_to_web/` оборачивается в неблокирующую координационную блокировку БД `pg_try_advisory_lock`, гарантируя, что сканирование ФС и ротацию файлов в `archive/` или `error/` в любой момент времени выполняет ровно один активный воркер. Внешние I/O-вызовы (SMTP, файловый шлюз) выполняются строго вне транзакции БД. При штатной остановке (`SIGTERM` в пределах `stop_grace_period`) воркер прекращает захват новых задач, дорабатывает текущую операцию, фиксирует результат в БД и завершается; при аварийном `SIGKILL` задача перехватывается другим воркером после истечения `locked_until` по модели **At-least-once**. Для исключения дублей транзакционных писем на стороне почтовых серверов и клиентов заголовок `Message-ID` в `integrations/mailer/smtp_client.py` формируется детерминированно из уникального идентификатора задачи (`BackgroundTask.id`). Жизнеспособность процесса контролируется обновлением штампа `heartbeat`.
* **Последствия:** Безопасное масштабирование `--scale worker=N` без гонок в БД и на файловом шлюзе; бесшовное сосуществование старых и новых воркеров во время релиза; отсутствие долгих блокировок строк в PostgreSQL при медленном SMTP и защита от потери писем без выделения отдельной таблицы `outbox`.

### ADR-007: Эшелонированная защита веб-форм и декомпозиция примитивов безопасности

### ADR-008: Доменная декомпозиция конфигурации (`pydantic-settings`), работа за Reverse Proxy (Nginx), внешние сессии и отдача статики Django 5.1
* **Контекст:** Требуется строгая валидация окружения при старте приложения, разделение настроек независимых подсистем, сокрытие секретов в трейсбеках, корректная работа Django за входным прокси Nginx (HTTPS-схема, клиентские IP для Rate Limiting, сохранность сессий при смене контейнеров `web`) и разгрузка Python-процесса от раздачи статики в production без поломки dev-режима и тестов.
* **Решение:** Использование системной переменной `APP_ENV` (по умолчанию `development`) с однократной каскадной загрузкой существующих файлов `.env` и `.env.{APP_ENV}` в функции `_env_files(base_dir)` с валидацией допустимых символов `APP_ENV` (защита от Path Traversal). Конфигурация разделена на 7 изолированных классов `BaseSettings` со своими префиксами (`DjangoSettings` — `DJANGO__`, `DatabaseSettings` — `DB_`, `RedisSettings` — `REDIS_`, `SecuritySettings` — `SECURITY_`, `ExchangeSettings` — `EXCHANGE_`, `CaptchaSettings` — `CAPTCHA_`, `SmtpSettings` — `SMTP_`), защищенных от мутации (`frozen=True`) и объединенных в агрегатор `AppConfig`. Чувствительные данные типизированы через `SecretStr` (с извлечением через `.get_secret_value()` в `config/settings.py`), строковые параметры валидируются типом `NonEmptyStr`. Для работы за Nginx в `config/settings.py` настраивается доверие прокси-заголовкам (`SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")`, проброс `X-Forwarded-For` для `IRateLimiter`), а пользовательские сессии выносятся из локальной памяти контейнера во внешний персистентный контур (PostgreSQL/Redis при едином `SECRET_KEY` окружения). Статика настраивается через словарь `STORAGES` Django 5.1: в `DEBUG = True` используется `StaticFilesStorage` (запуск без `collectstatic`), а в `DEBUG = False` — манифест `CompressedManifestStaticFilesStorage` для генерации хешированных URL на этапе сборки образа (`collectstatic --noinput`). В production скомпилированные артефакты публикуются в разделяемый том `static_volume` (без удаления файлов предыдущей ревизии в окне обновления) и отдаются напрямую через Nginx (read-only mount) в обход Gunicorn. В `LOCAL_APPS` на Этапе 1 подключаются `db.users.apps.UsersConfig` (с фиксацией `AUTH_USER_MODEL = "users.User"`) и `web.apps.WebConfig`; остальные пакеты `db.*` и `cli` регистрируются поэтапно по мере создания.
* **Последствия:** Полная разгрузка воркеров Gunicorn от раздачи статики в production при сохранении хеширования имен и совместимости ассетов в окне обновления `web`; сохранность клиентских сессий и точность Rate Limiting по IP за Nginx; невозможная мутация настроек в рантайме и чистая изоляция тестов.

### ADR-009: Мультиконтейнерная оркестрация (Docker Compose), входной контур Nginx, миграции Expand/Contract и бесшовное обновление
* **Контекст:** Требуется изолировать жизненный цикл прикладного кода от СУБД и кэша, закрыть внутренние сервисы от прямого внешнего доступа, исключить гонки применения миграций при масштабировании реплик и обеспечить независимое обновление и откат `web` и `worker` без потери данных и активных пользовательских сессий.
* **Решение:** Система разворачивается на одном хосте под управлением Docker Compose и разделена на 5 долгоживущих сервисов (`nginx`, `web`, `worker`, `postgres`, `redis`) и одноразовый служебный контейнер `migrate-job`. Сервисы `web`, `worker` и `migrate-job` запускаются из единого неизменяемого Docker-образа с фиксированным тегом релиза (связанным с коммитом), отличаясь только командами запуска, что исключает рассинхрон общих слоев (`core/`, `db/`, `services/`). Во внешнюю сеть публикуются исключительно порты `80`/`443` сервиса `nginx`, который терминирует TLS, отдает статику из read-only тома `static_volume`, защищает `/admin/` вторым рубежом (HTTP Basic Auth и/или IP Allowlist), Во внешнюю сеть публикуются исключительно порты `80`/`443` сервиса `nginx`, который терминирует TLS, отдаёт статику из read-only тома `static_volume`, защищает `/admin/` вторым рубежом (HTTP Basic Auth и/или IP Allowlist) и блокирует внешний доступ к `/exchange/`. Ре-резолвинг IP-адресов реплик `web` выполняется на уровне `upstream`-группы:

  ```nginx
  upstream web_upstream {
      zone web_upstream 64k;                      # resolve требует группу в shared memory
      server web:8000 resolve;                    # фоновый ре-резолв, hot-path без DNS
      resolver 127.0.0.11 valid=10s ipv6=off;     # встроенный DNS Docker
      resolver_timeout 5s;
      keepalive 32;} 
В location используется proxy_pass http://web_upstream совместно с proxy_http_version 1.1 и proxy_set_header Connection "". nginx опрашивает DNS в фоне по TTL valid=10s, подхватывает изменение состава реплик при --scale web=N и замену контейнера по схеме start-first без reload и без перезапуска периметра; keepalive-пул к бэкенду при этом сохраняется, а балансировка идёт по всему списку A-записей. Схема с set $backend "web:8000"; proxy_pass http://$backend; отклонена: она резолвит имя на каждый запрос (лишний DNS в hot-path), отключает keepalive по определению и не даёт балансировки между репликами.
Требование к платформе: OSS nginx >= 1.27.3 — параметр resolve у server в upstream и директива resolver в контексте upstream появились в 1.27.3 (ранее доступны только в nginx Plus). Версия фиксируется пинком точного тега образа (nginx:1.29-alpine); плавающий тег nginx:1.27-alpine запрещён, так как допускает сборку на 1.27.0–1.27.2, где конфиг не проходит nginx -t.
Выполнение `python manage.py migrate` вынесено из `entrypoint` контейнера `web` в одноразовый сервис `migrate-job` (`depends_on` с условием `service_completed_successfully`), а изменения схемы БД следуют стратегии **Expand/Contract** (только обратно совместимые расширения в текущем релизе; удаление устаревших полей — отдельным релизом после вывода старого кода). Порядок старта и готовность контролируются через `healthcheck`: `pg_isready` для `postgres`, `redis-cli ping` для `redis`, внутренний HTTP-эндпоинт `/healthz/` (без запросов к БД) для `web` и проверка свежести штампа `/tmp/worker_heartbeat` для `worker`. Обновление `web` выполняется по схеме `start-first` (через `docker-rollout` или `--scale web=2` с переключением трафика по готовности `healthy` и остановкой старой реплики по `SIGTERM`; резервный базовый режим — штатный `up -d` с окном 5–15 с), обновление `worker` — независимым пересозданием реплик через `SIGTERM` (`stop_grace_period`). Все персистентные данные вынесены в тома (`pgdata` со статусом `external: true` для защиты от случайного удаления через `down -v`, `redisdata`, `/app/cache`, `/exchange/`, `static_volume`), а том БД дополнительно защищен ежесуточным логическим бэкапом `pg_dump -Fc` на хосте вне контейнеров (с ротацией не менее 14 дней и регулярным тестовым восстановлением).
Система разделена на два L2-сегмента: edge (nginx ↔ web, публичный вход) и backend (web/worker ↔ postgres/redis, outbound через bridge). nginx не входит в backend; postgres/redis не входят в edge. Docker embedded DNS резолвит web в edge-IP для nginx и в backend-IP для postgres, поэтому upstream web_upstream и DB_HOST=postgres работают без изменений.
* **Последствия:** Полная сетевая изоляция внутренних сервисов; исключение гонок DDL-миграций и ошибок `502 Bad Gateway` при выкатке релизов; независимый и быстрый откат `web` и `worker` на предыдущий тег образа без отката схемы БД; гарантированная сохранность данных при пересоздании контейнеров. Полная сетевая изоляция внутренних сервисов; исключение гонок DDL-миграций и ошибок `502 Bad Gateway` при выкатке релизов; независимый и быстрый откат `web` и `worker` на предыдущий тег образа без отката схемы БД; гарантированная сохранность данных при пересоздании контейнеров; переиспользование TCP-соединений к бэкенду (keepalive-пул) и корректный ре-резолвинг реплик без `reload`. Плата — жёсткая привязка к nginx >= 1.27.3: версия образа пиннится и проверяется `nginx -t` на этапе сборки/деплоя; `gunicorn --keepalive` (75 с) держится выше `keepalive_timeout` nginx, иначе пул отдаёт закрытые соединения.

# ADR-010: Cloudflare как edge-прокси и доверенный источник CF-Connecting-IP

* **Контекст:** origin фактически принимает трафик через Cloudflare proxy, но зависимость нигде не зафиксирована; `$remote_addr` на nginx — адрес CF edge, что ломает `IRateLimiter` (ключи по IP) и аудит. Список доверенных сетей захардкожен в `nginx.conf`, только IPv4, устаревает без сигнала.
* **Решение:**
1. Статический `./nginx/nginx.conf` монтируется отдельным read-only bind; после изменения применяется через `scripts/cc.sh up -d --force-recreate nginx`, чтобы гарантированно перемонтировать файл после атомарной замены на хосте. Runtime-файлы `cloudflare-ips.conf` и `.htpasswd` лежат в исключённом из git `./data/nginx-dynamic/`, который монтируется целиком в `/etc/nginx/dynamic:ro`. Оба bind используют `create_host_path: false`. Для внедрения обновить `include` и `auth_basic_user_file` в `nginx.conf` на пути внутри `/etc/nginx/dynamic/`. `real_ip_header CF-Connecting-IP` применяется только к соединениям из `set_real_ip_from`; `real_ip_recursive` не включается.
2. Инвариант топологии: в CF DNS для origin публикуется только проксированная A-запись, AAAA отсутствует — CF→origin всегда IPv4.
3. Порты origin публикуются явно по IPv4 (`0.0.0.0`). IPv6 не включать до отдельной проверки сети Docker, сохранения исходного IP, публикации портов, `listen [::]`, IPv6-файрвола и обновления его allowlist; AAAA origin добавлять последней.
4. Файрвол: Docker с iptables backend, `DOCKER-USER` и `ipset` (`cf_ips_v4`, атомарный `swap`). Правила ограничивают только входящий трафик на опубликованные порты origin 80/443; учитывать, что `DOCKER-USER` обрабатывает пакеты после DNAT. Запрет устанавливается до публикации портов и восстанавливается при загрузке хоста до запуска ingress. Нативный nftables backend Docker требует отдельной схемы, без `DOCKER-USER`.
5. Bootstrap выполняет `deploy.sh`, не `cc.sh`: создаёт runtime-каталог, добавляет его в `.gitignore` на этапе внедрения и при отсутствии `cloudflare-ips.conf` устанавливает `nginx/cloudflare-ips.seed.conf` из git с правами `0644`. Seed не заменяет успешное получение списка для первичного открытия ingress. До запуска проверяется наличие `.htpasswd` и доступ на чтение от фактического UID/GID nginx worker с учётом отображения пользователей контейнера; файл не должен быть доступен на чтение остальным.
6. `.htpasswd` создаётся или редактируется во временном файле в том же каталоге (`htpasswd -c` только при создании), с выставлением владельца и прав до атомарной замены. Reload не нужен. Smoke-тесты после запуска и ротации: без credentials — `401` с ожидаемым `WWW-Authenticate`; с валидными credentials — ожидаемый ответ приложения без Basic Auth challenge. Один `401` не проверяет читаемость файла.
7. Ежедневный root-cron `scripts/update_cf_ips.sh`: абсолютные пути, `flock` на весь цикл, два HTTPS-запроса с таймаутами, проверка семейства и корректности CIDR, минимального числа уникальных префиксов (IPv4 ≥ 15, IPv6 ≥ 7) и запрет default route. При ошибке загрузки или валидации активное состояние не меняется. При смене списка сначала ограничить ingress пересечением активного и нового IPv4-списков; затем атомарно заменить include (временный файл в runtime-каталоге, `fsync` файла и каталога), выполнить `nginx -t`, reload и подтвердить переход nginx на новую конфигурацию: успешная отправка сигнала сама по себе не подтверждение. Только после этого открыть полный новый список в файрволе. При ошибке сохранить переходное ограничение, восстановить предыдущий include и подтвердить его повторную загрузку перед любым расширением ingress; вернуть ненулевой код и сигнализировать об ошибке. Если nginx остановлен, не считать обновление применённым: завершение перехода выполняется при следующем деплое после проверки запущенного nginx. Ошибку `cc.sh ps` отличать от пустого вывода успешной команды.
* **Последствия:** directory bind позволяет nginx видеть атомарные замены runtime-файлов; `IRateLimiter` и access-логи используют нормализованный IP клиента. В Django передаётся IP, сформированный nginx, а не произвольная входящая цепочка `X-Forwarded-For`. Файрвол и reload не образуют общей транзакции: переход через пересечение исключает открытие новых диапазонов до обновления доверия, но временно ограничивает доступ с изменившихся диапазонов.

# ADR-011: Единый источник DB_* (интерполяция вместо env_file-каскада)

* **Контекст:** postgres получает креды через compose-интерполяцию (`${DB_*}`, источник — shell  базовый `.env`), app-сервисы — через env_file-каскад (`.env`  `.env.{APP_ENV}`). Два механизма с разной семантикой допускают расхождение: переопределение DB_* в `.env.{APP_ENV}` или shell-export даёт auth-fail на migrate-job с запутанной диагностикой.
* **Решение:**
 1. `DB_NAME`, `DB_USER`, `DB_PASSWORD` передаются в `postgres`, `web`, `worker`, `migrate-job` через `environment:` с `${VAR:?}`-гардами: environment переопределяет env_file, каскад физически не может переопределить креды БД. Гарантия механизмная, не дисциплинарная.
 2. Инвариант: `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` — только в базовом `.env`; в `.env.{APP_ENV}` креды БД и `POSTGRES_*` запрещены (не-кредовые параметры `DB_*` разрешены); в базовом `.env` запрещены `POSTGRES_*` (grep с покрытием `export`-префикса). Условие применимости: один APP_ENV на хост; второе окружение на том же compose-проекте ломает инвариант — фиксировать отдельным ADR.
 3. `scripts/cc.sh` — единственный санкционированный вход к compose: нормализация CWD в корень репозитория, unset shell-override, read-only preflight env-файлов и источников bind-маунтов без создания файлов или каталогов, render-check с пробросом глобальных флагов compose, `exec docker compose "$@"`. Проверку источников bind пропускают команды, которые не создают маунты (`ps`, `config`, `logs`, `exec`); `exec` не считается read-only. Прямые вызовы compose вне cc.sh запрещены.
 4. L2 (санити рендера): сравнение `postgres.environment.POSTGRES_*` с `environment.DB_*` всех app-сервисов (`web`, `worker`, `migrate-job`) в одном `docker compose config --format json` (post-L0 обе стороны interpolated в одном рендере). Цель — регрессии compose-файла, не содержимое .env: swap внутри DB_* самосогласован и функционально безвреден. Self-test: `tests/test_render_check.py`.
 5. L3 (диагностика): migrate-job запускает `cli.preflight_migrate` — лог target (host/db/user) до `django.setup()`, на OperationalError hint с recovery-лестницей через `scripts/cc.sh exec postgres psql -U "<db_user>" -d postgres` (пароль / RENAME роли / RENAME БД / re-init как последний рубеж). Ключевой непокрываемый равенством источников кейс — init-only семантика тома: POSTGRES_* применяется только при первом init пустого pgdata. Отпечаток пароля — только за `MIGRATE_LOG_PWD_FINGERPRINT=1`.
 6. compose пиннен >= 2.24 (long-form env_file, корректный срез `export`-префикса); пароли — `[A-Za-z0-9]` (требование к генератору).
* **Последствия:** расхождение источников кредов БД невозможно по построению; fail-fast на config-стадии для пустых значений и чужого `--env-file`; секреты в `docker inspect` — не регрессия (уже так для postgres); диагностика auth-fail сводится к `scripts/cc.sh logs migrate-job`; цена — креды БД выведены из env_file-каскада, остальные доменные настройки ADR-008 не затронуты.

## 5. СТРУКТУРА СЛОЕВ И МОДУЛЕЙ ПРОЕКТА

Архитектура построена на принципах чистой архитектуры и 12-Factor App с параллельным расположением слоев в корне и изоляцией инфраструктурных контейнеров:

* **`config/`:** Инфраструктура проекта и Composition Root. Каскадная загрузка окружения (`.env` + `.env.{APP_ENV}`) через 7 изолированных классов `BaseSettings` (`pydantic-settings`), объединенных в агрегатор `AppConfig`. Инициализация настроек Django 5.1 (динамический `STORAGES` с генерацией манифеста `CompressedManifestStaticFilesStorage` на этапе сборки образа в том `static_volume` для отдачи статики напрямую через Nginx в обход Gunicorn, доверие заголовкам прокси `SECURE_PROXY_SSL_HEADER` и `X-Forwarded-For`, хранение сессий во внешнем персистентном контуре БД/Redis при едином `SECRET_KEY`, чтение `AppConfig`, подключение `db.users` (`AUTH_USER_MODEL = "users.User"`) и `web` на Этапе 1 с отложенным подключением остальных `db.*`/`cli` через `LOCAL_APPS`, константы прайса `PRICE_TEMPLATE_PATH`, `STORAGE_CACHE_DIR`, `PRICE_XLSX_FILENAME`), DI-контейнер `container.py` (`@lru_cache` синглтон `get_storage() -> IStorage` на Этапе 1 с прямой передачей `Path`-конфигов без двойного приведения; `get_catalog_xlsx_parser() -> ICatalogXlsxParser` с Этапа 2), маршрутизация верхнего уровня.
* **`core/`:** Базовые сущности ядра, абстрактные модели Django (`TimeStampedModel` с Этапа 1), протоколы/интерфейсы (`IStorage` на Этапе 1; `ICatalogXlsxParser` на Этапе 2; `IExchangeGateway` на Этапе 4; `IXlsxRenderer` на Этапе 5; `IRateLimiter`, `ICaptchaProvider`, `IMailer` на Этапе 7; `IChannelAdapter` на Этапе 10; `IOrderXlsxParser` на Этапе 12), чистые функции генерации криптографических токенов (`security.py`), доменные исключения (`FishWorkshopError`, `PriceNotAvailableError`).
* **`db/`:** Слой персистентности (Django ORM), разбитый на независимые доменные пакеты (минимальный скелет `db/users/` вводится на Этапе 1 до первого `migrate-job`; остальные пакеты — с Этапа 2):
  * `db/users/`: на Этапе 1 — минимальный каркас кастомной модели `User` (`email` + `UniqueConstraint(Lower("email"))`, пароль, `UserManager`, `UserAdmin`, `0001_initial.py`); с Этапа 2 — расширение бизнес-атрибутами (`JSONField` анкеты, профиль рассылки, признак B2B) и репозиторий пользователей (сохранение переходов состояния без бизнес-валидации).
  * `db/catalog/`: модели `Product`, `Category`, `CatalogSyncMeta` (с монотонной версией `version`), `MobileTradeSchedule`, репозиторий каталога и `admin.py` (форма ручного импорта каталога из `.xlsx` поверх `UploadedFile`, Этап 2).
  * `db/exchange/`: модели контроля сквозных номеров `ExchangeNodeState` и журнала дедупликации конвертов `ExchangePacketLog`, репозиторий обмена.
  * `db/tasks/`: модель персистентной очереди `BackgroundTask` (с полем времени аренды `locked_until` и версией схемы контракта `schema_version`), репозиторий задач с конкурентным захватом через `SELECT FOR UPDATE SKIP LOCKED` и фильтрацией выборки по поддерживаемым текущей версией кода `task_type` и `schema_version` (безопасная работа старых и новых воркеров в окне обновления).
* **`integrations/`:** Адаптеры к внешней инфраструктуре и техническим библиотекам:
  * `storage/`: адаптер локальной файловой системы `LocalFileSystemStorage` для работы с runtime-кэшем прайса `price.xlsx` с защитой от Path Traversal, `fsync` и атомарной перезаписью через временный файл.
  * `xlsx/`: технические адаптеры `openpyxl_parser.py` (реализация `ICatalogXlsxParser` на Этапе 2 и `IOrderXlsxParser` на Этапе 12, чтение из `BinaryIO` с `read_only=True, data_only=True`) и `openpyxl_renderer.py` (реализация `IXlsxRenderer` по мастер-шаблону, Этап 5).
  * `rate_limit/`: адаптер `redis_limiter.py` (реализация `IRateLimiter` на базе Redis, Этап 7).
  * `captcha/`: клиент Yandex SmartCaptcha и локальный `StubCaptchaProvider` (Этап 7).
  * `mailer/`: SMTP-клиент отправки транзакционных писем (`smtp_client.py`) с детерминированным формированием заголовка `Message-ID` из уникального идентификатора задачи (`BackgroundTask.id`) для защиты от дублей писем при политике повторов `At-least-once` (Этап 7).
  * `file_gateway/`: файловый шлюз `/exchange/` (Этап 4).
* **`services/`:** Слой прикладных сценариев (Use Cases) и бизнес-правил:
  * `xlsx_generator.py`: определение состава прайса, вызов `IXlsxRenderer` и публикация в `IStorage` с защитой от устаревших версий (Этап 5).
  * `catalog_service.py`: единая транзакционная синхронизация слепка ассортимента (`upsert` + деактивация отсутствующих позиций + инкремент `CatalogSyncMeta.version`) для ручного `.xlsx`-импорта (Этап 2, с Этапа 4 — admin-fallback) и `PRICE_SYNC` из 1С (Этап 4), плюс триггер пересборки кэша прайса в той же транзакции (Этап 5).
  * `price_delivery_service.py`: проверка бизнес-лимитов и капчи, возврат байтового потока прайса из `IStorage` и постановка задач на отправку по Email (Этап 7).
  * `account_service.py`: регистрация с паролем, подтверждение Email, восстановление доступа (Этап 7).
  * `subscription_service.py`: сохранение `JSONField`-анкеты, согласие по 152-ФЗ/ФЗ-38, переходы статуса подписки и атомарная запись событий `SUB_SYNC` / `UNSUB_EVENT` (Этап 8).
  * `exchange/`: пакет координации обмена (`contracts.py` — общие Pydantic-схемы конвертов; `processor.py` — нумерация, дедупликация в транзакции и выпуск `ACK_RECEIPT`; `handlers.py` — вызов прикладных сценариев, Этапы 4, 9).
* **`api/`:** REST JSON API на базе Django Ninja: Bearer-аутентификация, реэкспорт схем из `services.exchange.contracts`, единый роутер `POST /api/v1/exchange/`, принимающий трафик через входной прокси Nginx (Этап 4).
* **`web/`:** Пользовательский интерфейс (Django Templates, на Этапе 6 подключаются HTMX + Alpine.js):
  * Тонкие HTTP-контроллеры витрины, отдачи прайса (`IndexView`, `price_download_view` с `FileResponse`/`Http404`) и легковесный внутренний эндпоинт проверки готовности `/healthz/` (`200 OK` без обращения к БД для Docker `healthcheck` на Этапе 1).
  * Формы с валидацией Honeypot (`forms.py`), управление внешними Django-сессиями, контроллеры разового запроса прайса на Email, аутентификации и 3-шагового мастера подписки (Этапы 7–8).
* **`cli/`:** Инфраструктурный раннер фоновых процессов `worker_runner.py` (цикл опроса очереди по `locked_until` и `schema_version`, выполнение сетевых вызовов вне транзакции БД, координация поллинга `/exchange/1c_to_web/` между репликами `--scale worker=N` через блокировку БД `pg_try_advisory_lock`, обновление штампа `/tmp/worker_heartbeat` для Docker `healthcheck`) и Django management-команда запуска `run_worker.py` с обработкой сигналов штатного завершения `SIGTERM` (`stop_grace_period`, Этап 7).
* **`nginx/`:** Конфигурация входного reverse proxy (`nginx.conf`): единственная публичная точка входа (порты `80`/`443`), терминация TLS, редирект `80 -> 443`, прямая отдача `/static/` из read-only тома `static_volume`, защита `/admin/` вторым независимым рубежом (HTTP Basic Auth и/или IP Allowlist), блокировка внешнего доступа к `/exchange/` и динамический ре-резолвинг реплик `web` через `upstream`-группу с `resolve` и встроенным DNS Docker (`zone web_upstream 64k; server web:8000 resolve; resolver 127.0.0.11 valid=10s ipv6=off; resolver_timeout 5s; keepalive 32;`), `proxy_pass http://web_upstream` с `proxy_http_version 1.1` и `Connection ""` — без ручного `reload` и без потери keepalive-пула; требует OSS nginx >= 1.27.3 (пин тега образа обязателен).
* **`scripts/`:** Эксплуатационные скрипты управления жизненным циклом и защиты данных: `deploy.sh` (запуск одноразового контейнера миграций `migrate-job`, пополнение тома статики и бесшовное обновление `web`/`worker` по схеме `start-first`), `rollback.sh` (независимый откат `web` и `worker` на предыдущий неизменяемый тег образа без отката схемы БД) и `backup_db.sh` (ежесуточный логический дамп `pg_dump -Fc` на хосте вне контейнеров с ротацией архивов).
* **`assets/`:** Статические мастер-ресурсы (`assets/templates_xlsx/.gitkeep` на Этапе 1, эталонный шаблон `price_master_template.xlsx` с Этапа 5).
* **`exchange/`:** Физические каталоги файлового шлюза (`1c_to_web`, `web_to_1c`, `archive`, `error`), монтируемые во внутренний разделяемый том без публикации по HTTP.
* **`tests/`:** Автоматизированные тесты `pytest` (на Этапе 1: `conftest.py` с двусторонней очисткой синглтона хранилища до и после тестов, `test_storage.py`, `test_env.py`, `test_views.py`).
